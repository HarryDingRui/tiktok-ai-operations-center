# 运营中控台云端数据文档

网站保留 `data/real-store-data.js` 中的真实店铺名称、商品名称和商品 ID 目录。经营指标、日期快照和趋势数据按公开快照发布；价格利润页另读取经过精简和脱敏的订单、成本与定价快照。浏览器本地重新导入的数据仍优先于公开快照。

目录来源于 5 个 TikTok Shop 店铺：yaya112、yaya thailand tth、PETTOS、Miniyaya、INSPIRE PURIFY。`cloud-orders.json` 只保留价格利润核算所需字段，订单号会改写为 `PUB-xxxxxx`，不发布原订单号和达人账号；`cloud-pricing.json` 保留成本、活动价、建议零售价和费率，历史运费阶梯仅作为源数据存档。当前利润口径不读取重量，按每个商家成交额大于 0 的有效订单固定扣除 5฿ 运费。预估平台结算金额 = 商家成交额 − 平台总费用 − 固定运费；商家实际收入 = 预估平台结算金额 − 广告预估成本；毛利 = 商家实际收入 − 商品成本；订单净利润 = 毛利 − 人员与综合成本。

运营填报请使用同目录的 `tiktok-ai-operations-center-wps-kdocs-template.xlsx`，不要直接让运营编辑 JSON。该模板适合上传到 WPS/Kdocs，黄色区域是填报区，蓝色区域是公式或网站使用字段；网站“数据接入”页也提供直接下载入口。

## 更新方式

### 网页直接导入 product_list Excel

1. 打开网站的“数据接入”页面。
2. 点击“选择 product_list Excel 文件”，可一次多选 1 个或多个 `.xlsx/.xls` 文件。
3. 文件名建议保持 `店铺名：xxx-product_list_YYYYMMDD.xlsx`，网站会自动识别店铺名称和报表日期。
4. 导入后当前浏览器会立即刷新顶部店铺筛选、经营总览、GMV/销量 Top5 和商品明细，并按“店铺 + 报表日期”保存在该浏览器的本地存储中。

### 六类文件自动归类

数据接入页的“统一数据接入中心”支持一次选择多个 `.xlsx/.xls/.csv` 文件，也支持“导入整个导出文件夹”。网站按文件夹相对路径、文件名和表头识别以下六类：广告、商品、达人视频、达人、样品订单、联盟订单；文件日期优先读取文件名，店铺优先读取文件夹路径或已知店铺名。

选择“本地归类目录”后，网站会在用户授权的目录内创建 `店铺/数据类型` 文件夹并复制文件，原文件不会删除，同名文件会使用序号后缀避免覆盖；同时只在浏览器保存文件清单和归类路径，不把原始 Excel/CSV 提交到 GitHub。

GitHub Pages 不能在后台监听 D 盘，也不能替用户自动读取 TikTok Shop 导出动作。每次导出后仍需打开网站选择文件或导出文件夹；如果要完全做到“导出后无需打开网站就自动移动”，需要额外运行本地监听程序或带权限的后端服务。

### 日期范围和趋势口径

- 顶部“时间范围”支持“全部日期”“近7天”“近14天”和“自定义日期”。近7天/近14天以当前所选店铺（或全部店铺）的最新导入日期为结束日，不以电脑当天日期硬凑空数据。
- GMV、订单、曝光、CVR 和当前商品排行使用每个店铺在所选范围内的最新可用快照，避免把同一份累计快照重复相加。
- 商品明细同时保留商品成交件数、SKU订单数、预计客户数、平均订单金额、点击量、CTR、加购次数、加购率、CTOR 和去重点击CVR 等 product_list 原始字段。
- GMV 上涨/下降和 CVR 下降 Top5 使用所选范围内每个店铺的首个与最新快照，按同一商品 ID 匹配；单日筛选时会自动把该日之前最近的真实快照作为基线，区间汇总指标不会混入基线日期。
- 因此，要查看真实的 7 天、14 天变化，需要继续导入对应日期的同格式文件；单日筛选只会在存在前一份真实快照时生成日环比，缺少基线时保持“待导入”，不以 0 或推算值代替。

静态 GitHub Pages 不会把浏览器本地导入结果同步给其他人；如果要让所有访问者看到同一批新数据，需要把生成后的数据文件重新发布，或接入带权限的后端数据服务。

### Control Plane 闭环

- `ops-control-plane.js` 负责动作记录、T+1/T+3/T+7 验证、知识库审核和 Agent 本地任务历史。
- 动作与知识记录保存在当前浏览器的 localStorage；支持 CSV/XLSX，知识库另支持 MD/TXT。
- Agent 当前是可审计的本地规则引擎：会真实读取当前浏览器已导入的数据，但不会伪装成已连接 WPS/Kdocs、Seller Center 或外部 LLM。接入这些服务仍需后端 API、权限和部署配置。
- “有效/无效”只有在有对应日期快照和指标阈值，或导入了明确证据时才生成；缺失数据保持“待验证”。

### 公开快照更新（需要重新发布）

1. 运行 `scripts/generate_profit_cloud_snapshot.py`，传入订单表、SKU 成本映射表、价格利润核算表和仓库路径。
2. 生成器会重写 `cloud-orders.json`、`cloud-pricing.json`，并更新 `cloud-import.js` 中的版本和数据地址。
3. 运行 `tests/profit-cloud-sync.test.js` 以及项目其余测试后，提交到 `main` 分支。
4. 公开快照是发布时的数据，不会自动读取员工电脑；后续要自动同步最新私有数据，仍需要带权限的后端服务。

如果使用 WPS/Kdocs：先填写模板，再导出对应 CSV。当前 GitHub Pages 仍是静态站点，本次真实商品数据作为公开静态快照发布；后续要自动同步最新私有数据，仍需要后端 API 和权限控制。

## 数据分区

- `storeStats`：全部店铺和各店铺总览指标、成交来源占比。
- `alertSummary`：商品预警页的高风险、中风险、低风险和今日检测商品汇总；演示数据替换时应与预警明细保持同一统计口径。
- `products`：旧版演示数据中的商品/链接、销量、GMV、变化和预警字段。
- `real-store-data.js`：公开商品目录，只包含店铺名、商品名和商品 ID；经营指标必须由用户重新导入真实 `product_list` 文件。
- `actions`：运营已执行动作、负责人、验证节点、证据和结论。
- `publishTrend`：每日自营发布量。
- `bd`：达人合作与交付汇总。
- `ads`：广告汇总和广告计划明细。
- `video`：自营短视频汇总。
- `knowledge`：真实导入或由验证有效动作沉淀的运营方法论、适用场景和验证指标；审核状态保存在本机。
- `店铺字典`：维护真实店铺名称和编码；“全部店铺”只是汇总口径，不代表只有当前示例店铺。
- `五组排行`：基于商品数据公式生成销量 Top5、全店 GMV Top5、GMV 上涨 Top5、GMV 下降 Top5、CVR 下降 Top5。
- `预警规则`：维护曝光、GMV、CTR、CVR 等阈值和运营处理队列。
- `运营知识库` / `Agent调度`：记录真实导入的有效方法、审核状态、Agent 任务输入与本地复核历史；团队复用次数需要后端或团队协作数据源才能统计。
- `云文档说明`：给运营看的 WPS/Kdocs 上传、填写、导出和网站接入流程。

## 口径要求

- 缺失数据使用 `null`，不要用 0 代替未知。
- GMV 使用数字字段，网站负责格式化金额。
- 百分比字段按“数值百分比”填写，例如 `3.86` 表示 `3.86%`。
- 运营动作的 `result` 只有在 T+1/T+3/T+7 有真实证据时才填写有效或无效，否则保持待验证。
- 商品预警阈值为：曝光下降超过 20%、GMV下降超过 15%、CTR下降超过 0.5 个百分点、CVR下降超过 0.3 个百分点；缺少对比数据时保持待导入。
- 本次真实数据是单周期快照；没有上一份真实快照时，GMV 上涨/下降和 CVR 下降排行保持“待导入上一周期”，不以 0 或推算值代替。
