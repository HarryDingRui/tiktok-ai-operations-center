# TikTok AI 运营中心动态登录页设计

## 状态

已获得用户对推荐方案的实施确认；本文件用于在修改代码前锁定范围、认证边界和验收标准。

## 目标

把公司内网 Docker 部署当前的 Nginx Basic Auth 浏览器原生弹窗，升级为一个可定制、带克制动态效果的“TikTok AI 运营中心”登录页，同时保持现有中控台业务页面、GitHub Pages 部署和现有账号体系不受影响。

## 当前事实

- 项目是纯静态 HTML/CSS/JavaScript，没有前端构建工具。
- `index.html` 是现有中控台入口，不包含应用级登录页面。
- 内网 Docker 部署由 Nginx 提供静态文件服务，当前通过 `auth_basic` 保护页面。
- GitHub Pages 是静态公开部署，不能承担密码校验或安全会话。
- 现有账号凭据只允许保存在内网服务器的 `.secrets` 中；不得进入 GitHub、镜像、前端代码、日志或 Obsidian。

## 非目标

- 不重做现有中控台仪表盘、数据页面或业务逻辑。
- 不把密码、App Secret、API Key 写入前端或 Compose 文件。
- 不把 GitHub Pages 改造成带真实认证的后端系统。
- 第一阶段不增加角色权限、团队邀请、找回密码或多因素认证。

## 推荐架构

### 组件

1. **登录静态页面**
   - 新增独立的 `login.html`、`login.css`、`login.js`。
   - 只负责呈现、表单交互和调用认证接口。
   - 不保存密码，不把凭据写入 `localStorage`。

2. **内网认证服务**
   - 新增独立的 Node.js 20+ `services/auth-gateway` 服务。
   - 使用 Node 原生 HTTP 与 `crypto`，保持与现有 Feishu 网关一致，不引入不必要的运行时依赖。
   - 账号密码哈希和会话签名密钥从服务器挂载的 secret 文件读取。
   - 现有账号沿用，不在仓库中保存明文密码。

3. **Nginx 认证边界**
   - `/login`、登录页面资源和登录/登出/会话检查接口公开。
   - 其他页面与静态资源通过 Nginx `auth_request` 检查 HttpOnly 会话 Cookie。
   - 未认证的页面请求重定向到 `/login`；接口请求返回 401，避免把 JSON 请求误导向 HTML。
   - 保留 `/healthz` 的免认证健康检查。

4. **Docker Compose**
   - 静态 Nginx 与认证服务位于同一内部网络。
   - 认证服务不暴露宿主机端口，只允许 Nginx 访问。
   - 两个服务均配置健康检查和 `restart: unless-stopped`。

### 会话规则

- 登录成功后签发 HttpOnly、SameSite 会话 Cookie。
- 在 HTTPS 部署时启用 Secure；当前内网 HTTP 阶段按实际协议配置，不能假装具备 HTTPS 的安全属性。
- 会话默认短时有效，认证服务重启会使临时会话失效。
- 登出清除 Cookie；过期、签名不合法或用户不存在均按未认证处理。
- 错误提示不区分“用户不存在”和“密码错误”，避免泄露账号信息。

## 视觉与交互设计

### 视觉方向

登录页采用“运营中枢 / COMMAND CENTER”风格，而不是普通 SaaS 表单：

- 深海军蓝和近黑背景，延续当前侧栏的品牌基调。
- 青蓝色用于认证通道和数据流，橙色只用于警示或关键状态。
- 中央登录面板保持清晰、稳重、可读，不使用大面积模糊玻璃或装饰性渐变。
- 标题、状态和按钮使用高对比度文字，兼容桌面和移动端。

### 动态效果

- 背景为低频率、低对比度的数据节点与扫描光圈。
- 登录面板使用一次性入场动画，不持续抖动。
- 输入框聚焦显示认证通道状态，按钮提交后显示加载状态并禁止重复提交。
- 成功、失败、网络错误分别有明确状态反馈。
- `prefers-reduced-motion: reduce` 下关闭粒子、扫描和浮动效果，保留必要的状态变化。
- 动画只使用 CSS/原生 JavaScript，避免 CDN、远程字体和外部动画依赖。

### 登录状态

- 初始：`内网安全认证通道 · 等待验证`
- 提交中：`正在验证访问权限...`
- 成功：短暂显示 `认证通过，正在进入运营中枢`
- 凭据错误：`账号或密码错误，请重新输入`
- 网关不可用：`认证服务暂时不可用，请联系管理员`
- 会话失效：`登录已过期，请重新认证`

## GitHub Pages 兼容策略

- 不修改现有 `index.html` 的页面路径和相对资源路径。
- GitHub Pages 继续以静态公开网站运行；它不启用内网 Nginx 的 `auth_request`。
- 登录页文件可以随仓库发布，但没有内网认证服务时不得显示“认证成功”或伪造登录状态。
- 所有真实凭据校验只发生在公司内网 Docker 部署。
- 通过 Nginx 配置差异实现“同一套前端静态文件、不同部署认证边界”，不删除现有 Pages 配置。

## 验收标准

### 认证

1. 未登录访问内网根路径会进入自定义登录页，而不是浏览器原生弹窗。
2. 正确账号可以进入原有中控台，原有业务页面显示不变。
3. 错误账号、错误密码、篡改 Cookie、过期 Cookie 都不能进入。
4. 刷新页面保持有效会话；登出后再次访问需要登录。
5. 认证服务停止时页面不会假装登录成功，Nginx 和健康检查状态可观察。

### 视觉与体验

1. 桌面端登录页有完整动态背景、清晰表单和成功/失败状态。
2. 移动端不发生横向溢出，键盘操作可完成登录。
3. 关闭减少动态效果后仍然可用，动画不会阻塞内容显示。
4. 不加载公网字体、CDN 图片或第三方脚本。

### 部署与安全

1. `docker compose config` 通过。
2. 认证服务和静态服务镜像构建通过。
3. `/healthz` 返回 200 且不要求登录。
4. 账号密码和会话密钥不出现在 Git diff、镜像层、浏览器源码或日志中。
5. GitHub Pages 继续可以正常发布和访问原有静态页面。
6. 现有前端回归测试、认证服务测试和 Docker smoke test 全部通过。
